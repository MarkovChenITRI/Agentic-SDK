# Spec: Playground 的使用體驗落差

**Status:** ready-for-agent

## Problem Statement

使用者照著 Builder 的五個問題做完一個 agent，得到的東西和他選的不一樣。

最基本的用法就會遇到：選「不需要查資料」做一個聊天助理，問它「用一句話說明什麼是保固」，它回答「目前沒有足夠的資料」。

更難發現的是安靜失效的那些：選「沒把握就停下來」，那道保護從來沒有生效過；選第二個記憶選項，什麼都不會發生；Builder 顯示五題全部完成、可以開始使用，其中兩題的答案是編出來的，按下執行失敗。

這些都不是崩潰。四十四個請求零個 5xx。是設定、畫面與實際行為三者對不上。

## Solution

Builder 上顯示的每一件事，都是這個 agent 實際的行為。使用者選什麼就得到什麼，得不到的時候，畫面說得出原因。

## User Stories

1. 身為想做聊天助理的人，我希望選了「不需要查資料」之後 Agent 會直接回答我，這樣我不必先猜出要自己寫一段回覆規範。
2. 身為想做查表機器人的人，我希望「用對照表命中固定內容」真的只是查表，這樣它便宜又可預測。
3. 身為開了防幻覺保護的人，我希望那道保護真的會擋，這樣我能信任它。
4. 身為 Builder 使用者，我希望畫面上顯示的答案就是我的 agent 的設定，這樣我看得懂自己做了什麼。
5. 身為 Builder 使用者，我希望畫面說「可以開始使用」的時候，按下去真的能用。
6. 身為 Builder 使用者，我希望選項承諾的事情真的會發生，否則那個選項不要出現。
7. 身為 Runner 使用者，我希望失敗時看得出缺什麼，這樣我能補上再試。

## Implementation Decisions

**票 01 和 02 各自獨立，可以先做。** 一個修預設回覆規範與檢索選項的矛盾，一個讓三個 retrieve 模組用同一種方式回報命中數。兩者都不牽涉產品定位。

**票 03 和 05 要一起決定，因為它們的答案互斥。** 票 03 的一種修法是把預設答案套進 spec，那會讓每個 agent 都帶上模型；票 05 的方向則是讓純查表的 agent 成為可能。先決定「Builder 是一份要填完的表單，還是一組可以只改一格的預設值」。

**票 04 不能取代 01、02、03。** 它讓已知的失敗說出原因；那三張是讓失敗不要發生。

## Testing Decisions

好的測試驗證使用者看得到的行為，不驗證實作細節。

**這批問題現有測試全部沒抓到，原因值得記下來。** 單元測試各自驗證單一模組，都通過；缺的是「照使用者的順序走完 Builder，然後真的對話」這一條。票 02 的例子最清楚：現有測試自己手工建一個 `ContextEntry(metadata={"hit_count": 0})` 餵給 reflect，從來沒有跑過真實的 retrieve 模組，所以鍵名不一致測不出來。

**接縫沿用既有的：** HTTP 路由（Flask test client）與 `build_workflow(spec, endpoint_selections)`。新增的測試要跨過「Builder 說的」與「Runner 做的」之間，而不是在任一側各自驗證。

## Out of Scope

語意檢索的向量化路徑——本次驗證環境沒有 embedding 模型，那一段未實際執行。

`runner_service` 內部以中文關鍵字判斷使用者意圖的啟發式規則。

## Further Notes

證據來自 2026-09-02 的本地驗證：Playground 跑在本機，模型端點指向本機 Ollama，照真實使用者的方式按順序回答 Builder 的問題，然後實際對話。

**先前有一版以程式碼缺陷為單位的票已作廢。** 那一版把問題寫成「某個函式少了一個分支」，而且其中一項結論（「`EvidenceCheckReflect` 任何選項都選不到」）是錯的——它來自把每個選項孤立套用在預設 spec 上，那不是任何人的操作方式。這一版全部改以使用者遭遇的事情為單位。
