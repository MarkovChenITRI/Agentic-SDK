# 06: Q1 的第二個選項承諾了記憶，但什麼都不會發生

**What to build:** Q1 的兩個選項，選了要有不同結果；做不到就不要出現。

**Blocked by:** 無，可立即開始

**Status:** wontfix

- [x] 待評估

## 使用者遭遇的事

Q1「這個 Agent 主要要完成哪類任務？」的兩個選項：

```
in_context               只根據目前這次對話內容產生問答，不參考先前互動。
workflow_recall_preview  問答時需要接續先前互動內容或狀態。
```

第二個選項對使用者承諾了跨互動的記憶。實測兩個選項組出來的 agent 完全相同，對話行為也完全相同。spec 會把 `workflow_recall_preview` 強制轉回 `in_context`，連 Builder 表單回讀都顯示 `in_context`——**使用者的選擇連視覺上都留不住**，而且沒有任何訊息。

## 缺的評估：接上去，還是拿掉

選項名稱帶著 `preview`，看起來是有人打算做但沒做完。SDK 側其實有 `PersistentMemory` 和 `InMemoryStore.search()`，底層能力存在。

**選項 A — 拿掉。** 從 Q1 移除，等真的要做再加回來。現況是最差的：看得到、選得到、什麼都不會發生。

**選項 B — 接上去。** 需要先回答還沒答的設計問題：記憶存在哪（現在只有暫存目錄的 session 檔）、怎麼隨使用者隔離、多久過期、AI Hub 上的 agent 分享出去時記憶跟不跟著走。

傾向 A，因為選項 B 的設計問題不小，而現況每天都在對使用者說謊。

## 決定（2026-09-02，已更正）：保留，這是商業策略不是缺陷

**先前的決定（移除選項）已回退。**

`workflow_recall_preview` 灰掉鎖起來是刻意的：它是在對使用者說明 `CrossContextMemory` 的布局——這個產品打算往哪裡走。移掉它等於移掉那個訊息，而不是移掉一個壞掉的功能。

我把「點不下去的選項」當成對使用者的假承諾，但一個明確標示「預覽中」、明確不可點的選項並沒有承諾它現在能用；它宣告的是方向。這兩件事不一樣，我當初沒有分辨。

而且這個判斷本來就不是我的：產品要對外揭露什麼路線圖，是商業決定。

## 這張票真正的教訓

程式碼裡看起來「沒有作用」的東西，不一定是缺陷。`available=False` 的選項、`_is_locked_builder_choice` 裡那段永遠不會執行的判斷——我看到的是死碼，實際上是刻意保留的機制。刪掉之前要先問它為什麼在那裡。

`tests/test_playground_contracts.py::test_the_preview_memory_option_stays_locked_and_visible` 現在釘住這個行為。
