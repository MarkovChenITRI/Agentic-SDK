# 語音代理：聽得懂、講得出、可以被打斷

**Status:** ready-for-agent

## Problem Statement

一個 Agent 只能用打字對話。使用者想用講的，而且講到一半發現方向不對時，想直接開口打斷它——就像跟人說話那樣。

現在做不到，而且不是「還沒接語音 API」這麼簡單：工作流一旦開始回答就跑到底，沒有任何地方可以停。使用者只能等它講完，或關掉重來。

## Solution

Builder 多兩個選項：Q2 可以選「語音對話」，Q4 可以選「語音回覆」。兩個獨立——只選輸入是用講的取代打字，只選輸出是只想聽它講，兩個都選就是完整的語音對話。

選了語音輸入的 Agent 會一直聽著。使用者一開口，它就停止當下的回答，把使用者沒聽到的那段從對話記錄裡拿掉，然後聽完新的問題再接著回。

選了語音回覆的 Agent 會同時給兩個東西：**說出的內容**是口語的重點與判斷理由，**顯示的內容**是需要看的精確資料。兩者互相補充，不是把畫面上的字唸一遍。

## User Stories

1. 身為使用者，我想用講的代替打字，這樣雙手在忙的時候也能問問題。
2. 身為使用者，我想在 Agent 講到一半時直接開口打斷，這樣我不用等它講完不相干的內容。
3. 身為使用者，我打斷之後想接著問，而不是重新開始一輪，這樣對話不會被切斷。
4. 身為使用者，我打斷之後 Agent 應該知道我聽到了哪裡，這樣它不會重複我已經聽過的話。
5. 身為使用者，我打斷之後 Agent **不應該**提起我沒聽到的內容，這樣它不會引用一段我沒聽過的話。
6. 身為使用者，我想聽到口語化的重點，同時在畫面上看到精確的資料，這樣我不用把型號和價格用聽的記下來。
7. 身為使用者，我不想聽 Agent 把畫面上的表格逐字唸出來，這樣才像對話而不是朗讀。
8. 身為使用者，我在安靜的房間裡不說話時，Agent 不應該自己被觸發，這樣它不會憑空打斷自己。
9. 身為使用者，我在吵雜環境中，Agent 不應該把背景聲音當成我在說話。
10. 身為使用者，我講話中間停頓想一下，Agent 不應該以為我講完了就搶著回答。
11. 身為使用者，我想只用語音輸入但看文字回覆，這樣在圖書館也能用。
12. 身為使用者，我想只聽語音回覆但用打字輸入，這樣在吵雜環境也能用。
13. 身為建立者，我想在 Builder 選「語音對話」，這樣不用寫程式就能做語音 Agent。
14. 身為建立者，我想知道選了語音之後要綁哪些模型，這樣我不會做出一個開不起來的 Agent。
15. 身為建立者，我選了語音輸入但沒選語音回覆，系統不該擋我，這是一個合理的組合。
16. 身為建立者，我想在編輯流程裡改回非語音，而不用重建 Agent。
17. 身為 SDK 使用者，我想用 `Workflow(perceive=VoiceTextPerceive(...), action=VoiceAnswerAction(...))` 宣告語音 Agent，形狀跟其他模組一致。
18. 身為 SDK 使用者，我不想因為只用文字就被迫理解語音模組。
19. 身為 SDK 使用者，我想在測試裡驅動整條插話流程，而不用連到雲端服務。
20. 身為維護者，我想在軌跡上看到「這一輪是被打斷的」，而不是看到一個錯誤。
21. 身為維護者，我想知道打斷發生在哪一個模組執行中，這樣我能判斷是不是打太早。
22. 身為維護者，我不想因為部署設定改變（例如加了 worker）就讓插話靜默失效。
23. 身為維護者，我想知道語音功能花了多少額度，尤其是沒人講話的時候。
24. 身為訪客，我從畫廊點進一個語音 Agent，我想直接開口就能用，不必先按什麼按鈕。
25. 身為訪客，我拒絕給麥克風權限時，Agent 應該告訴我它需要什麼，而不是靜靜地不動。

## Implementation Decisions

### 角色與模組

語音**不新增第六個工作流角色**。`VoiceTextPerceive` 佔 perceive 角色，`VoiceAnswerAction` 佔 action 角色。

Spike 已驗證現有的模組契約撐得住（`spikes/realtime-interjection/`）：模組是 Workflow 持有的物件，活得比單次回合久，所以可以在建構時開啟音訊連線並持續存在；而取消權杖是整個 run 共用的同一個物件，所以 perceive 在自己回合抓住它之後，背景執行緒能停掉稍後執行的 action。

**輸入在 perceive，輸出在 action。** 曾經考慮讓 perceive 同時擁有兩個方向，理由是「一個地方擁有音訊通道」——但轉寫與語音合成根本不是同一條連線（前者是長連線 WebSocket，後者是每次回答一條串流請求），那個整合是想像出來的。見 `docs/adr/0001-where-voice-lives.md`。

`VoiceAnswerAction` 繼承 `GenerativeAction`，加上產生**說出的內容**與呼叫語音合成。既有的 `GenerativeAction` 一行都不動。

**說出的內容是選用欄位。** 沒有它的 action 就把顯示的內容唸出來——能動，只是照本宣科。

### 打斷

**打斷靠語音活動偵測，不等轉寫。** 實測：開口到 `speech_started` 約 610 ms，完整轉寫約 3.9 秒。等文字再停就不叫打斷了。

收到開口訊號時，依序做三件事（取自 OpenAI Realtime 的做法）：

1. **前端立刻停止播放**，讓使用者感知到的延遲是一個影格
2. **記下已播放的時長**——使用者實際聽到多少
3. **截斷上下文**：把使用者沒聽到的那段從對話記錄移除

第三步是這次 survey 才補上的，而且是必要的：保留使用者沒聽到的文字，會讓下一輪的 Agent 引用一段沒人聽過的話。

`interrupt_payload` 回報的是**使用者聽到的時長**（來自前端播放位置），不是模型產生的字數。模型產生多少與使用者聽到多少是兩件事，只有後者對下一輪有意義。

後端在收到取消後中止語音合成串流，這是為了省額度，不影響使用者感知。

### 記憶

被打斷的回合在記憶中留下**使用者實際聽到的那一段**，並標記為被打斷。下一輪的系統提示明說「上一輪你講到一半被打斷，他聽到了以下內容」，要求承接而非重述。

實測過不記錄的後果：Agent 回答「沒有足夠資料指出前一段具體停在哪裡」。

### 客戶端靜音過濾（必要，非最佳化）

實測 3 秒純靜音：計費 30 audio tokens（與有內容的 3 秒相同），且**被辨識成「这里」**——憑空產生的文字。若不在客戶端過濾，安靜的房間會持續產生假輸入並觸發打斷。

以本地音量門檻過濾：低於門檻不上傳，偵測到音量下降後多送一段避免切掉句尾。門檻可調，預設值以實測環境音決定。

### Builder

Q2 新增「語音對話」（第四個選項），Q4 新增「語音回覆」。兩個獨立，四種組合都合法：

| 組合 | 意義 | 綁定 |
| --- | --- | --- |
| 都不選 | 現況 | 依既有規則 |
| 只選 Q2 | 用講的取代打字 | transcribe |
| 只選 Q4 | 只想聽它講 | TTS |
| 兩個都選 | 完整語音對話 | transcribe + TTS |

綁定規則不變：模組需要什麼端點就要求什麼。

`VoiceTextPerceive` **不呼叫模型**，轉寫結果原樣往下傳，所以選語音輸入不需要綁 perceive 端點。代價是口語的不完整與語助詞會直接進入 plan 與 retrieve；這是 PoC 的取捨，列為後續工作。

### 邊界

**取消能力在 SDK，音訊在 Playground。** 模組標準不知道麥克風存在。

瀏覽器音訊經過 Playground 的 WebSocket 端點再轉發到語音服務，金鑰不進瀏覽器。`playground/main.py` 已是 FastAPI 掛載 Flask，加端點不需更換伺服器。

**Playground 必須單一行程。** 打斷訊號與它要停止的工作流必須共用記憶體。啟動時檢查，多於一個 worker 就明確拒絕——靜默失效是最糟的失敗模式。

**SDK 加入 `websockets` 依賴**（PoC 求快；日後可改為選用額外套件）。

### 跨區

語音模型部署在 `eastus2`，Playground 執行環境在 `southeastasia`，實測 RTT 約 200 ms。接受。真正的延遲瓶頸不在網路，而在「等下一個串流片段才檢查取消」的約 900 ms，那靠前端先停就掩蓋掉。

## Testing Decisions

好的測試只驗**外部行為**：使用者做了什麼、系統回應了什麼。不驗私有方法、不驗某個函式被呼叫幾次。

### 接縫

盡量用既有接縫，只新增一個。

**接縫一（既有）：`run_agent(spec, ...)`** — 涵蓋 spec 到行為的一切：語音 spec 建得起來、要求正確的綁定、打斷會停、被打斷的內容進了記憶、下一輪銜接得上。既有測試大量使用這個接縫。

**接縫二（既有）：`apply_builder_step` / `build_spec`** — Builder 答案到模組與綁定需求。四種語音組合的綁定表在這裡驗。

**接縫三（新增）：音訊傳輸介面** — 唯一的新接縫。`VoiceTextPerceive` 與 `VoiceAnswerAction` 透過一個可注入的傳輸物件與外部服務往來：輸入端能送出音訊、回報開口、回報轉寫；輸出端能收文字、串流回音訊、可被取消。

測試用假的傳輸驅動整條鏈路（「現在觸發開口」「現在回傳這段轉寫」），**不需要網路也不需要憑證**。真實實作只是這個介面的一種。傳輸參數是選用的：不傳就用三件式端點參數建立預設實作，所以 README 的範例不會出現它。

不為瀏覽器端另開接縫——WebSocket 端點用既有的路由測試方式即可。不為打斷另開接縫——取消權杖已在核心，spike 的兩個測試已釘住。

### 既有的類似測試

- `tests/test_playground_contracts.py`：Builder 答案、綁定需求、`run_agent` 行為
- `tests/test_unit_documented_modules.py`：模組層行為，含 spike 加入的兩個取消測試
- `tests/support.py` 的 `FoundryOpenAILikeClient`：假的模型客戶端，音訊傳輸替身照這個形狀做

### 要涵蓋的行為

靜音不上傳；有聲音才上傳；開口觸發打斷；打斷後記憶只留使用者聽到的部分；沒聽到的部分不出現在下一輪的上下文；四種 Builder 組合各自要求正確的綁定；沒有說出的內容時退回唸顯示的內容；多 worker 時啟動被拒絕。

## Out of Scope

- **本地 VAD 模型**（如 WebRTC VAD，可分辨人聲與冷氣聲）。先用音量門檻。
- **`semantic_vad`**：以模型判斷語句是否完整，對口語停頓應優於純靜音門檻。有回報指出 Azure 曾忽略此設定，需先實測。列為第一個後續改善。
- **`VoiceTextPerceive` 用模型理解輸入**：目前原樣傳遞轉寫結果。
- **講者分離**（`gpt-4o-transcribe-diarize`）。
- **把語音模型搬到 southeastasia**，或在 eastus2 另開一份執行環境。
- **多行程部署**：明確拒絕，不是待辦。
- **語音附件**（在語音對話中傳圖片）。

## Further Notes

Spike 的完整量測與踩過的坑在 `spikes/realtime-interjection/README.md`，包含兩個會讓人卡很久的細節：尾端沒有靜音時語音活動偵測永遠不會判定語句結束；服務要求 16 kHz 而語音合成產出是 24 kHz。

打斷流程參考 OpenAI Realtime 的既有做法（`conversation.item.truncate` 與 `audio_end_ms`）。他們刪除未播放部分的文字紀錄，理由與我們相同：避免上下文中存在使用者沒聽過的內容。

`docs/adr/0001-where-voice-lives.md` 記錄了為什麼放棄讓 perceive 同時擁有輸出——那個理由（兩個方向不共用連線）是設計過程中才發現的，未來的讀者不會自己想到。
