# Spec: Builder 承諾與 Runner 實際行為的落差

**Status:** ready-for-agent

## Problem Statement

使用者在 Builder 裡做完所有選擇，Builder 顯示「可以開始使用」，按下執行卻得到「暫時無法產生回覆。」。訊息沒有說明缺了什麼，畫面上也沒有任何待補項目。

這不是邊角情況。十二個 Builder 選項各跑一次真實對話，**三個在使用者沒做錯任何事的情況下失敗**，而且是最常用的三個之一：選關鍵字檢索、選語意檢索、把失敗策略設成重試。

另有一個選項按下去完全不會發生任何事，而且不會有任何提示。

## Solution

Builder 問使用者的問題，涵蓋 Runner 實際需要的每一項；Builder 顯示「可以開始」時，執行就真的會成功。做不到的時候，訊息說出缺什麼。

## User Stories

1. 身為 Builder 使用者，我希望我選了檢索方式之後 agent 跑得起來，這樣我不必猜哪裡出錯。
2. 身為 Builder 使用者，我希望畫面說「可以開始使用」的時候它真的可以開始，這樣那個狀態才有意義。
3. 身為 Builder 使用者，我希望我照著畫面把每個要綁的端點都綁完之後就能執行，而不是綁完了還是失敗。
4. 身為 Builder 使用者，我希望知道自己的選擇連帶啟用了哪些模組，這樣我才知道要為什麼東西做設定。
5. 身為 Builder 使用者，我希望我選的記憶類型真的生效，或者那個選項不要出現。
6. 身為 Runner 使用者，我希望執行失敗時看得出是哪裡缺了什麼，這樣我能自己補上再試。
7. 身為維護者，我希望「哪些角色需要模型」只有一個定義，這樣不會有一處判斷正確、另一處漏掉的情況。
8. 身為維護者，我希望不能用的函式不要留在程式碼裡，這樣下一個人不會以為它可以用。

## Implementation Decisions

**票 01 是根因，其餘四張各自獨立。** 判斷「哪些角色需要模型」的 `reachable_openai_roles` 是對的；把它轉成使用者要填項目的 `_deployment_requirements` 漏了 plan。同時 `_plan_from_config` 只會去借 action 角色的端點，所以即使使用者綁了 reflect 也沒用。兩者必須一起修，只補一邊仍然會失敗。

**票 01 與票 03 的答案互相決定，同一輪 grilling 一起談。** 使用者不知道自己裝了 plan（票 03），所以不會想到要為它綁端點（票 01）。若票 03 選擇「把檢索與規劃拆成兩個問題」，票 01 的 UI 負擔就變成使用者自己的選擇。

**票 04 不是票 01 的替代品。** 它把已經知道的失敗原因說出來；票 01 是讓 Builder 一開始就知道少了什麼。

## Testing Decisions

好的測試驗證對外行為，不驗證實作細節。

**接縫沿用既有的：** HTTP 路由（Flask test client，已有二十八個測試在用）與 `build_workflow(spec, endpoint_selections)`。這次的缺陷全部發生在「Builder 說的」與「Runner 做的」之間，所以驗證要跨過那個接縫——建一個 spec、問 Builder 要求綁什麼、照著綁、然後執行，斷言成功。

**現有測試沒抓到的原因值得記下來：** 單元測試各自驗證 `reachable_openai_roles` 與 `_deployment_requirements`，兩者都通過，但沒有測試把「Builder 要求的綁定」餵回「Runner 的執行」。缺的是這一條，不是更多單元測試。

## Out of Scope

`runner_service` 內部回應塑形邏輯的拆分，以及那批以中文關鍵字判斷使用者意圖的啟發式規則。

語意檢索的向量化路徑——本次驗證環境沒有 embedding 模型，那一段未實際執行。

## Further Notes

證據來自 2026-09-02 的本地驗證：`PLAYGROUND_TEST_MODE` 加上指向本機 Ollama 的模型端點，十二個 Builder 選項各跑一次真實對話。四十四個請求，零個 5xx，所以這些不是崩潰，是設定與執行之間的落差。

同一次驗證確認相符的部分：每個選擇只改動它該改的模組、session 隔離正常、多輪對話累積正確、匿名不能存回 AI Hub。
