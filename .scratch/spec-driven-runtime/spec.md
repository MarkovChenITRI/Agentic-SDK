# Spec: 執行層改以 spec 為單一來源

**Status:** ready-for-agent

## Problem Statement

Playground 把每個 agent 的設定存成兩份。第一份是 JSON 結構，程式裡稱為 spec。第二份是從 spec 編譯出來的 Python 程式碼文字。

程式碼文字的用途是給人閱讀的匯出品。負責這件事的模組在開頭寫明它「永遠不會被反向解析」。

實際執行 agent 的時候，程式不讀 spec。它讀那份程式碼文字，再用語法解析把設定拆回來。

這造成三個使用者看得到的結果。

**設定會消失。** 有七項設定在 spec 裡通過驗證、甚至被夾限範圍，卻沒有被寫進程式碼文字，所以執行時拿不到：流程的三個上限值、進入點模組、記憶種類、規劃階段的 system prompt、檢索的筆數上限、輸入理解的重要度、輸出格式。使用者在 Builder 裡設定它們，看起來成功了，執行時卻沒有作用。

**同一個 agent 從不同路徑載入，行為不同。** 從 AI Hub 載入 agent 有兩條路由。其中一條在載入後重新編譯程式碼文字，另一條沒有。因為執行層讀的是那份文字，走後者載入的 agent 會用過期的設定執行。

**Builder 的問答邏輯寫了兩份。** 每個選擇題的答案都要改變設定，而這個轉換實作了兩次，一套改 spec，一套改程式碼文字。兩套已經漂移：一套處理六種失敗策略，另一套只處理兩種。

## Solution

執行層直接接收 spec。

編譯成程式碼文字的函式保留，但只往單向流動：它產生給人閱讀的預覽，以及存回 AI Hub 的匯出欄位。沒有任何程式再把它讀回來。

草稿狀態只保存 spec。需要程式碼文字的兩個地方在需要時當場計算，所以不存在會過期的副本。

七項設定在資料流換向之後接上，成為第一次真正生效。

## User Stories

1. 身為 Builder 使用者，我希望我在流程上限欄位填的值真的生效，這樣我設定的保護才有意義。
2. 身為 Builder 使用者，我希望我選的記憶種類真的生效，這樣 agent 的記憶行為才符合我的選擇。
3. 身為 Builder 使用者，我希望我為規劃階段寫的 system prompt 真的送到模型，這樣我才能調整它的判斷方式。
4. 身為 Builder 使用者，我希望我設定的檢索筆數上限真的生效，這樣回覆引用的資料量才可控。
5. 身為 Builder 使用者，我希望我選的輸出格式真的生效，這樣回覆的形態才符合我的情境。
6. 身為 Builder 使用者，我希望我設定的進入點模組真的生效，這樣流程才從我指定的地方開始。
7. 身為 Builder 使用者，我希望我設定的輸入理解重要度真的生效，這樣記憶的權重才符合我的意圖。
8. 身為 Runner 使用者，我希望不論從哪一條路徑載入 agent，它的行為都一樣，這樣我才能信任我看到的結果。
9. 身為 Runner 使用者，我希望我載入的 agent 用的是它最新的設定，這樣我不會拿到一份過期的行為。
10. 身為 AI Hub 的協作者，我希望別人分享給我的 agent 執行起來和作者看到的一樣，這樣分享才有意義。
11. 身為 AI Hub 的協作者，我希望公開列表上的 agent 仍然看得到、載得動，這樣這次改動不會弄丟既有內容。
12. 身為 Builder 使用者，我希望同一個選擇題不論從哪個畫面回答，結果都一致，這樣我不必記住哪條路徑會有不同行為。
13. 身為維護者，我希望設定只有一個來源，這樣我修一個設定相關的 bug 只需要看一個地方。
14. 身為維護者，我希望新增一個設定欄位時不必同時改編譯器和解析器，這樣新增設定的成本是一份而不是兩份。
15. 身為維護者，我希望測試能斷言某個設定真的到達執行期，這樣我才驗證得了設定有沒有生效。
16. 身為維護者，我希望移除死掉的程式碼，這樣讀這個模組的人不會誤以為它們是活的。
17. 身為之後接手的 agent，我希望執行入口的名字描述它的職責，這樣我從名字就知道它做什麼。
18. 身為之後接手的 agent，我希望建構 workflow 的函式是公開介面，這樣我測試它時不必去 monkeypatch 私有名稱。
19. 身為之後接手的 agent，我希望這個專案的詞彙表定義了 Agent 這個詞，這樣我用它命名時有依據。
20. 身為維護者，我希望這次改動的每一步都能單獨驗證，這樣出問題時我知道是哪一步。
21. 身為維護者，我希望「行為不變」的改動與「行為改變」的改動分開，這樣測試變紅時我分得出原因。
22. 身為維護者，我希望刪除舊路徑之前先確認沒有資料依賴它，這樣刪除不會弄壞生產環境。

## Implementation Decisions

**執行層接收 spec 字典，不接收已經轉換好的設定物件。** 呼叫端手上本來就是 spec，不必多學一個型別；轉換的位置從六處收斂成一處；內部使用的設定物件維持不變，所以執行層內部的大量程式碼不受影響。這次改動的風險只落在資料怎麼進來，不落在資料進來以後怎麼用。

**不定義新的設定型別。** 目前只有一種設定來源，新型別解決不了任何實際問題。

**入口以職責命名，不以輸入格式命名。** 這一層做的事是跑一個 agent，不是跑一份 spec。名字寫成輸入格式的話，輸入格式再變一次就得再改一次名字。

**建構 workflow 的函式從私有升為公開介面。** 它已經是事實上的接縫——十三個測試 monkeypatch 它。公開之後，設定是否到達執行期才有辦法直接斷言。

**四個語意檔案路徑參數收斂成一個。** 它們由同一個上傳識別碼算出來，四個一起出現或四個都不出現，沒有第三種情況。

**移除從未被比對的 fingerprint。** 它在載入時重算一次就把舊值丟掉，唯一的效果是強迫四個呼叫點傳入程式碼文字。要不要做成真的功能，是獨立的產品決定。

**編譯成程式碼文字的函式保留。** AI Hub 的兩支公開查詢都要求對應欄位非空，欄位空掉的話 agent 會從公開列表消失，公開載入回 404。

**草稿只保存 spec。** 過期副本的問題因此直接消失，不必等到後續的 session 收攏工作。編譯是純函式，只會被兩個不頻繁的路徑呼叫。

**刪掉從程式碼文字推導 spec 的相容路徑。** 草稿存在暫存目錄，設定為非永久，Azure App Service 重啟或重新部署都會清掉。這段相容處理保護的窗口只有單次請求的長度。

**建立 `CONTEXT.md`，只定義 Agent 一個詞。** 專案的 domain 文件規則要求詞彙延後建立，在詞真的被釐清時才寫。這次被釐清的是：Agent 是一份 spec 加上執行它所需的環境設定，而 Workflow 是 SDK 裡執行它的那個東西。這個區分正是改名的依據。

**改動排成 expand–contract，不排成垂直切片。** 執行入口的型別一改，數十個測試呼叫點同時斷掉，沒有任何垂直切片能單獨保持綠燈。所以先把測試 fixture 換成新的建構方式（expand），再翻轉型別（migrate），最後刪掉舊路徑（contract）。

**刪除舊路徑之前要有生產環境的查證。** 那些依版本分流的判斷是唯一擋在舊資料前面的東西。查證是人工任務，需要資料庫權限。

## Testing Decisions

好的測試只驗證對外行為，不驗證實作細節。斷言的對象是介面回傳的東西，不是某個變數叫什麼名字或某段程式碼長什麼樣。

**三個接縫，由高到低。**

第一個是 HTTP 路由，用既有的 Flask test client。已經有二十八個測試在用。行為不變的驗收在這裡做，因為它證明整條鏈還通。載入路徑不一致的 bug 也在這裡驗證，因為那個 bug 就是兩條路由行為不同，只有從外面看才看得到。

第二個是執行入口本身，已經有三十八個直接呼叫。fixture 遷移在這個接縫上做，斷言不動，只換建構方式。

第三個是建構 workflow 的公開介面。七項設定的驗收在這裡做——其中幾項在 HTTP 層看不出來，例如規劃階段的 system prompt 要看送給模型的內容才知道，流程上限要讓流程真的繞很多圈才觸發。拿到 workflow 物件直接斷言比在 HTTP 層製造這些條件可靠。

**既有的測試慣例。** 這個 repo 用 pytest，測試模組在 import 期就會載入 Flask 應用，所以測試設定必須在 conftest 就固定下來，與開發者本機的雲端憑證無關。模型呼叫一律用假的 OpenAI 相容用戶端，測試支援模組已經提供。

**不會動到的部分。** 執行層內部有二十幾個私有名稱被測試直接呼叫。它們屬於另一個重構主題，這次不修，也不讓它們變多。

## Out of Scope

Builder 狀態機的統一。它是獨立的票，需要自己的設計。

Session 草稿狀態的收攏。它是獨立的票，且範圍會因為本 effort 而縮小。

執行層內部回應塑形邏輯的拆分，以及那二十幾個私有名稱的測試 reach-in。

前端 JavaScript 沒有介面、只能用文字比對測試的問題。

SDK 端的所有改動。記憶型別判定、`Workflow.run()` 的狀態性、Plan 的路由政策都在另一個 effort。

那批未被引用的前端模組、無法到達的場景設定機制、以及其他死結構的清理。

## Further Notes

這份規格來自一次架構檢視加上五輪 grilling，共十五項決定。決定的完整清單見各張票的 Comments。

七項設定接上去之後會改變既有 agent 的行為，其中流程上限最明顯——它會改變中止時機。這件事要寫進變更紀錄。

另一個 effort（`sdk-breaking-change`）處理 SDK 端。它的第一張票是文件變更，沒有相依，可以隨時進行；第二張票需要自己的設計。兩者與本 effort 沒有阻塞關係。
