# 02: 讓 Plan 的路由政策有接縫

**What to build:** Plan 模組問模型下一步要查資料還是直接回答，然後用一份內建的中文零售關鍵字表推翻模型的答案。這份表寫在通用 SDK 裡，改它就得改 SDK。改成由呼叫方提供這條規則。

**Blocked by:** sdk-breaking-change/01

**Status:** done

- [x] 詞表移除，改為 `route_policy` adapter
- [x] 子字串閘門移除，`retrieve_description` 明確保存
- [x] 發布衛生測試補上那批詞彙
- [x] 變更紀錄寫明破壞性變更

## Comments

**缺的資訊：** 這張票需要自己的 `/grilling`，主要決定政策介面的形狀，以及 SDK 要不要附一個預設政策。

**已知事實一：** 這份關鍵字表包含試穿、門市、取貨、調貨、庫存、現貨、展示品、品號、遊樂場。它是這個套件裡改動最頻繁的檔案之一，因為每個新案例都是一次編輯字面值。

**已知事實二：** 啟用這個覆寫的條件，是對模組自己的 system prompt 做子字串比對。所以傳入自訂 system prompt 會同時廢掉 retrieve 說明與整個覆寫機制，沒有錯誤訊息。反過來，一個剛好含有那個英文片語的 prompt 會啟用呼叫方從沒要求過的中文關鍵字表。這個組合目前沒有測試。

**已知事實三：** 專案的發布衛生測試禁止個案詞彙出現在 SDK 裡，但它的黑名單沒有涵蓋上面那九個詞，所以測試是綠的。設計時要一併決定黑名單怎麼補。

**完成之後：** 發布 0.2.0，變更紀錄寫清楚改了什麼。

## 完成記錄

**先確認覆寫在生產環境是活的。** 任何 `retrieve_description` 非預設的 agent——例如帶檢索目標的 semantic agent——它的規劃決策都會被那九個中文零售關鍵字推翻。這不是理論問題。

**介面：** `NextStepPlan(..., route_policy=None)`。政策收到 state 與模型選的模組，回傳最終要用的模組。SDK 不附預設政策——「哪些問題需要查資料」取決於題材，那是應用程式知道而通用規劃器不知道的事。

**同時修掉那個互相抵銷的參數組合。** 傳入 `system_prompt` 原本會同時丟掉 `retrieve_description` 並關閉覆寫，因為閘門是對模組自己的 prompt 做子字串比對。現在兩個參數都保留，且有測試涵蓋——這個組合先前沒有任何測試。

**測試：** 三個只差在填哪個中文詞的測試，換成三個測介面的測試：沒有政策時採用模型的決定、有政策時採用政策的決定、自訂 prompt 不會丟掉檢索描述。

**發布衛生測試的黑名單補上那九個詞**，它們原本就漏掉了，所以那批詞彙在 SDK 裡待了很久而測試一直是綠的。補上之後立刻抓到另一處外洩：`runner_service.py` 的人工接手訊息假設 agent 在賣有庫存的商品，已改成領域中立的說法。
